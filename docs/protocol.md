# PC-98 FAT12 파일 패치 패키지·세트 프로토콜

이 문서는 패치 ZIP 제작자와 호환 적용기 구현자가 따라야 할 계약을 정의합니다. 배포 단위는 전체 HDM 패치가 아니라 FAT12 논리 파일마다 만든 BPS입니다. 결과 HDM은 적용 시 사용자가 가진 원본에서 결정론적으로 다시 조립합니다.

## 역할과 책임

패키지 제작자는 배포 ZIP에 넣는 논리 파일 패치와 부가 문서의 배포 가능성을 판단합니다. 제작 도구는 content HDM에서 레시피에 선언된 파일 내용만 읽으며, 전체 목표 HDM이나 클러스터 여유 공간·미할당 영역을 패치 입력으로 사용하지 않습니다.

적용기는 사용자가 로컬에서 고른 패치 ZIP과 원본 HDM을 검사하고 결과를 재현합니다. BPS가 표현할 수 있는 일반 바이트를 저작권·소유권 관점에서 분류하지 않으며, FAT 파일 바깥 영역을 보편적으로 금지하는 정책도 두지 않습니다. 이 프로토콜 자체가 배포 payload를 선언된 논리 파일 BPS로 한정합니다.

웹 참조 구현은 파일을 서버로 전송하지 않습니다. 이는 적용기의 실행 경계에 관한 사실이며, 패키지 제작자의 배포 책임을 대신하지 않습니다.

한 작품이 여러 결과 매체를 필요로 할 때도 각 결과는 독립된 기존 단일 패키지가 소유합니다. 상위 패치 세트는 어떤 결과가 함께 완료되어야 하는지와 그 패키지 바이트 정체만 결합하며, 내부 BPS나 FAT12 조립 규칙을 다시 정의하지 않습니다.

## 적용 순서

```text
패치 ZIP 크기·항목 검사
  → recipe.json 엄격 파싱
  → 선언된 patches/*.bps만 제한 크기로 해제
  → 각 BPS 구조·메타데이터·동작 범위 검사
  → 원본 HDM 크기·SHA-256·FAT12 형상 검사
  → 선언된 원본 논리 파일·LHA 멤버·빈 입력만 확정
  → 파일별 copy 또는 BPS 적용·목표 파일 해시 검사
  → 사용자 원본에서 결과 HDM 결정론적 조립
  → 결과 SHA-256·FAT12 구조 검사
  → 결과 HDM 제공
```

한 단계라도 실패하면 부분 결과나 다운로드 파일을 제공하지 않습니다. 화면의 레시피 요약은 안내용이며 Rust 코어의 검사가 적용 권한을 가집니다.

## ZIP 구조

작품별 배포물은 일반 ZIP 하나입니다.

```text
<작품명>-kr-patch.zip
├── recipe.json
└── patches/
    ├── GAME-COM.bps
    └── DATA-BIN.bps
```

- `recipe.json`은 ZIP 루트에 정확히 하나 있어야 합니다.
- `bps` 변환 항목의 `patch_key`에는 정확히 `patches/<patch_key>.bps` 하나가 대응해야 합니다.
- `copy` 변환에는 BPS가 없어야 합니다.
- `patches/` 아래의 누락·중복·미선언 항목은 오류입니다.
- 의미 있는 항목은 암호화할 수 없고 `Stored` 또는 `Deflated`만 허용합니다.
- `README.txt` 같은 `patches/` 바깥 부가 항목은 허용하지만 적용기는 읽거나 압축 해제하지 않습니다.
- ZIP 바깥 파일명은 사람을 위한 배포 이름이며 원본·호환성 판정에 쓰지 않습니다.
- 원본·content·결과 HDM, 저장 데이터와 내부 검수 자료는 넣지 않습니다.

위 경로 규칙은 새 형식 기준입니다. 기존 호환 형식은 ASCII 출력 이름을 패치 키로 사용하므로 종전의 `patches/NAME.EXT.bps` 경로를 그대로 읽습니다.

## 다중 결과 패치 세트

원본 디스크 수가 아니라 패치 적용 뒤 반드시 함께 있어야 하는 **결과 매체 수**가 둘 이상이면 일반 ZIP 하나에 기존 단일 패키지를 바이트 그대로 넣습니다. 결과가 한 장뿐이면 원본 작품이 여러 장이어도 단일 패키지를 그대로 배포합니다.

```text
<작품명>-kr-patch.zip
├── patch-set.json
└── packages/
    ├── disk-a.zip
    └── disk-b.zip
```

`patch-set.json`은 UTF-8 JSON 객체이며 선언되지 않은 필드를 거부합니다.

```json
{
  "format": "retrogame-patcher-pc98-fat12-package-set",
  "id": "example-game-complete-set",
  "title": "예제 게임 한글패치",
  "members": [
    {
      "key": "disk-a",
      "label": "디스크 A",
      "package_size": 1234,
      "package_sha256": "<소문자 SHA-256>"
    }
  ]
}
```

- `format`은 정확히 `retrogame-patcher-pc98-fat12-package-set`입니다.
- `id`와 `title`은 비어 있지 않아야 하며 적용 판정에는 쓰지 않습니다.
- `members` 배열 순서는 화면 표시와 결과 제공 순서입니다. 모든 구성원이 필수이며 1개 이상 32개 이하입니다.
- `key`는 영숫자로 시작하는 1~64바이트 안전한 ASCII 식별자이며 영숫자·`_`·`-`·`.`만 허용합니다. 구성원마다 달라야 합니다.
- `label`은 사람이 결과 매체를 구별하는 비어 있지 않은 표시 문자열입니다.
- 각 구성원에는 정확히 `packages/<key>.zip` 하나가 대응하며 `package_size`와 `package_sha256`이 그 ZIP 바이트와 일치해야 합니다.
- `packages/` 아래의 누락·중복·미선언 항목은 오류입니다. 루트 `recipe.json`과 `patch-set.json`을 함께 둘 수 없습니다.
- 내포한 ZIP은 이 문서의 지원 단일 패키지여야 합니다. 패치 세트를 재귀적으로 넣을 수 없습니다.
- 내포한 ZIP은 이미 압축된 자료이므로 참조 작성기는 `Stored`로 기록합니다. 소비자는 `Stored`와 `Deflated`를 모두 받을 수 있지만 ZIP 압축 방식·항목 순서·시각에 의존하지 않습니다.
- 구성원 사이에서 원본 또는 결과 HDM SHA-256이 어느 역할로든 중복되면 하나의 입력을 어느 필수 매체에 대응할지 모호하므로 제작과 적용을 거부합니다.

외부 ZIP 이름, 구성원 `key`·`label`, 사용자 HDM 파일명과 선택 순서는 입력 매체를 판정하지 않습니다. 적용기는 먼저 길이로 불가능한 후보만 제외한 뒤, 전체 파일의 SHA-256이 내포 레시피의 `source.sha256` 또는 `target.sha256`과 정확히 같은지 확인합니다. 길이는 사전 필터이며 SHA-256만 대응 관계를 확정합니다.

원본 해시와 맞는 입력은 적용 예정, 결과 해시와 맞는 입력은 이미 적용됨입니다. 같은 필수 구성원에 다시 대응한 파일은 중복, 어느 해시에도 맞지 않는 파일은 지원하지 않는 입력으로 보고합니다. 여분 입력이 있어도 모든 필수 구성원이 정확히 하나씩 채워졌으면 적용할 수 있지만, 여분을 조용히 성공 입력으로 세지 않습니다. 입력 파일 수가 구성원 수와 같은지만으로는 준비 완료가 될 수 없습니다.

원본 상태인 구성원은 내포 단일 패키지로 적용하고, 정확한 결과 상태인 구성원은 바이트를 그대로 결과로 이어받습니다. 모든 구성원의 목표 SHA-256이 확인된 뒤에만 전체 성공과 구성원별 다운로드를 제공합니다. 한 구성원이라도 누락되거나 실패하면 부분 성공을 표시하지 않습니다.

작성 도구의 `set-plan.json`은 배포물이 아닌 로컬 제작 입력입니다. `id`, `title`, `members[].key`, `members[].label`과 매니페스트 파일 위치를 기준으로 해석하는 `members[].package_path`를 가집니다. 상대 경로는 계획 파일이 있는 디렉터리를 기준으로 하며, 배포 `patch-set.json`에는 호스트 경로가 들어가지 않습니다.

```sh
cargo run --release --manifest-path patch-core/Cargo.toml \
  --bin pc98_patch_author -- create-set \
  set-plan.json game-complete-kr-patch.zip
```

## recipe.json

`recipe.json`은 UTF-8 JSON 객체입니다. 모든 객체는 선언되지 않은 필드를 거부하며 SHA-256은 소문자 64자리 16진수만 허용합니다.

| 필드 | 의미 |
| --- | --- |
| `format` | 아래 형식 식별자 중 하나 |
| `id` | 파일 BPS 메타데이터와 결합할 비어 있지 않은 패치 식별자 |
| `title` | 화면에 표시할 작품·패치 이름 |
| `output_filename` | 결과 다운로드 파일명. `/`와 `\` 금지 |
| `source` | 지원 원본 이미지의 크기·SHA-256·FAT12 형상·마운트 정책 |
| `assembly` | 보존 파일과 순서가 있는 배치 파일 목록 |
| `target` | 결정론적으로 조립되는 최종 이미지의 크기와 SHA-256 |

배포판 번호는 별도 프로토콜 필드가 아닙니다. 필요하면 ZIP 이름, `title`, `output_filename`에 표시하되 적용 판정은 내용 정체에만 의존합니다.

새 패키지는 `retrogame-patcher-pc98-fat12-raw-sfn-file-bps`를 사용합니다. 이 형식은 FAT 이름의 원시 11바이트와 ZIP 내부의 안전한 `patch_key`를 분리합니다. 기존 `retrogame-patcher-pc98-fat12-file-bps`는 ASCII DOS 이름을 패치 키로도 쓰던 공개 패키지를 재현하고 적용하기 위한 호환 형식입니다. 기존 형식의 의미와 공개 벡터는 바꾸지 않습니다. `format`만이 조립 의미를 선택하며, 파일명·디스크 내용·실행 환경으로 형식을 추론하거나 다른 조립기로 fallback하지 않습니다. 조립 의미를 바꿔야 한다면 새 형식 식별자가 필요합니다.

### 원본과 FAT12 형상

`source.size`와 `source.sha256`이 먼저 일치해야 합니다. `source.geometry`에는 BPB의 다음 값을 모두 기록합니다.

- `bytes_per_sector`
- `sectors_per_cluster`
- `reserved_sectors`
- `fat_count`
- `root_entries`
- `total_sectors`
- `media_descriptor`
- `sectors_per_fat`
- `sectors_per_track`
- `heads`

형상은 이미지 크기와 일치하고 FAT12 클러스터 범위여야 합니다. `target.size`는 `source.size`와 같습니다.

`source.mount_policy`는 다음 중 하나입니다.

- `standard`: BPB를 그대로 사용합니다.
- `pc98_dos3`: DOS 3 계열 PC-98 BPB임을 선언합니다. 원시 FAT12 구현은 선언된 형상을 직접 읽고, 호스트 FAT 라이브러리를 쓰는 구현만 마운트용 메모리 복사본의 후기 BPB 필드와 IBM 부트 서명을 호환값으로 보정할 수 있습니다. 어느 경우에도 결과 예약 영역은 사용자 원본 바이트여야 합니다.

## 원본 파일 선택

`assembly.retained_files`는 원본 루트에서 그대로 남길 파일입니다. 각 항목은 FAT 이름 `name`, `size`, `sha256`을 가집니다.

`assembly.placed_files`는 결과 루트에 새로 놓을 파일이며 배열 순서가 FAT 작성 순서를 결정합니다. 각 항목의 변환 입력은 다음 필드로 고정합니다.

| 필드 | 의미 |
| --- | --- |
| `patch_key` | ZIP 항목과 BPS 메타데이터에만 쓰는 안전한 논리 식별자 |
| `name` | 결과 루트에 기록할 FAT 이름 |
| `source` | 변환 입력을 얻을 위치 또는 빈 입력 |
| `source_size` | 변환 입력 길이 |
| `source_sha256` | 변환 입력 SHA-256 |
| `transform` | `copy` 또는 `bps` |

루트 파일은 다음처럼 선언합니다.

```json
{ "kind": "root_file", "name": "GAME.COM" }
```

ASCII로 온전히 표현할 수 없는 FAT SFN은 점을 포함한 표시 문자열로 변환하지 않고, 디렉터리 엔트리의 이름 11바이트를 소문자 16진수로 선언합니다. 아래 값은 CP932 `道草異聞` 8바이트와 `DAT` 3바이트입니다.

```json
{
  "kind": "root_file",
  "name": { "raw_sfn_hex": "93b9919088d995b7444154" }
}
```

MZ 실행 파일 뒤 LHA 멤버는 다음처럼 선언합니다.

```json
{
  "kind": "mz_lha_member",
  "container": "INSTALL.EXE",
  "member": "GAME.COM"
}
```

LHA 헤더의 이름 바이트도 호스트 문자열 변환 없이 직접 선택할 수 있습니다. FAT SFN과 달리 LHA 이름에는 점이 실제 바이트로 들어갑니다.

```json
{
  "kind": "mz_lha_member",
  "container": "INSTALL.EXE",
  "member": { "raw_name_hex": "93b9919088d995b72e444154" }
}
```

원본에 없던 새 파일은 빈 바이트열을 변환 입력으로 선언합니다.

```json
{ "kind": "empty" }
```

`empty`의 `source_size`는 `0`, `source_sha256`은 빈 바이트열의 SHA-256인 `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`여야 합니다. 이 소스는 원본 HDM에서 어떤 파일도 읽지 않습니다. `bps` 변환이면 0바이트를 소스로 새 파일 전체를 만들고, `copy` 변환이면 길이 0인 새 파일을 만듭니다.

문자열 FAT 이름은 ASCII 대문자 8.3이며 영숫자와 `_`, `$`, `~`, `-`, `.`만 허용합니다. `raw_sfn_hex`는 정확히 11바이트를 나타내는 소문자 22자리 16진수여야 하며 FAT의 빈·삭제 엔트리 표식, 비어 있는 파일명 본체와 점 디렉터리 이름은 거부합니다. 원시 이름은 CP932로 디코딩하거나 유니코드로 정규화하지 않습니다.

새 형식의 모든 배치 파일은 `patch_key`를 가져야 합니다. 키는 1~64바이트 ASCII이며 영숫자로 시작하고 영숫자·`_`·`-`·`.`만 쓸 수 있습니다. FAT 이름과 패치 키는 각각 중복될 수 없습니다. 기존 호환 형식은 `patch_key`를 받지 않고 ASCII 출력 이름을 키로 사용합니다. 실제로 요구한 루트 파일과 LHA 멤버만 읽으며 MZ 길이, LHA 헤더·CRC, 해제 길이와 SHA-256을 모두 확인합니다.

## 파일 변환

변경하지 않는 파일은 다음과 같습니다.

```json
{ "kind": "copy" }
```

결과 파일은 검증된 원본 논리 파일과 완전히 같습니다. 대응 BPS는 없습니다.

변경 파일은 다음과 같습니다.

```json
{
  "kind": "bps",
  "target_size": 12345,
  "target_sha256": "<소문자 SHA-256>"
}
```

`target_size`와 `target_sha256`은 제작 도구가 content HDM의 해당 논리 파일에서 계산해 배포 `recipe.json`에 기록합니다. 파일 크기는 원본과 달라도 됩니다. 결과의 전체 선언 파일 수는 루트 엔트리 수를, 결과 파일 길이 합은 이미지 크기를 넘을 수 없습니다.

## 파일 BPS 결합

각 `patches/<patch_key>.bps`는 표준 `BPS1`입니다. BPS 소스와 목표는 HDM 전체가 아니라 해당 변환 입력과 결과 논리 파일입니다. `empty` 소스의 BPS 입력은 정확히 0바이트입니다.

새 형식의 BPS 메타데이터는 다음 필드만 가진 UTF-8 JSON입니다. `target_sfn_hex`에는 ASCII 이름도 공백 패딩한 실제 11바이트를 기록합니다.

```json
{
  "format": "retrogame-patcher-pc98-fat12-raw-sfn-file",
  "recipe_id": "<recipe.id>",
  "patch_key": "GAME-COM",
  "target_sfn_hex": "47414d4520202020434f4d",
  "source_size": 123,
  "source_sha256": "<placed_files.source_sha256>",
  "target_size": 456,
  "target_sha256": "<transform.target_sha256>"
}
```

기존 호환 형식은 기존 메타데이터 식별자 `retrogame-patcher-pc98-fat12-file`과 `output_name` 필드를 그대로 사용합니다.

적용기는 BPS 마법값, 소스·목표 크기, 메타데이터, 정규 가변 길이 정수, 동작 수와 모든 복사·리터럴 범위, 소스·목표·패치 CRC32를 검사합니다. 메타데이터는 레시피에서 정규 직렬화한 값과 바이트 단위로 같아야 하므로 다른 파일이나 레시피의 BPS를 바꿔 끼울 수 없습니다.

참조 구현은 BPS1 처리를 공개 [retro-patch-utility](https://github.com/mcpads/retro-patch-utility)에 위임하고 Cargo Git 의존성을 정확한 커밋 SHA로 고정합니다.

## 결과 HDM 조립

### 기존 ASCII 호환 형식

`retrogame-patcher-pc98-fat12-file-bps`는 최초 공개 당시의 조립 의미를 그대로 유지합니다. 참조 구현은 원본의 메모리 복사본을 `fatfs` 0.3.6으로 열고, 보존하지 않는 항목을 라이브러리의 삭제 동작으로 제거한 뒤 `placed_files` 순서대로 ASCII 파일을 생성합니다. `pc98_dos3` 보정은 마운트 복사본에만 적용하며 언마운트 뒤 예약 영역을 원본 바이트로 되돌립니다. 공개 ASCII 적합성 벡터와 각 레시피의 `target.sha256`이 최종 판정 기준입니다. 새 원시 조립 규칙이나 파일별 FAT 설정을 이 형식에 소급 적용하지 않습니다.

### 원시 SFN 형식

결과 바이트는 다음 규칙으로 조립합니다. 별도로 “알아서 정하는” FAT 배치나 시각 값은 없습니다.

1. 입력 HDM을 같은 길이의 작업 이미지로 그대로 복제합니다. 구현이 `pc98_dos3` 마운트 호환 보정을 필요로 한다면 작업 중 메모리 복사본에만 적용합니다. 모든 배치가 끝나면 마운트 정책과 관계없이 예약 영역 전체가 원본 바이트와 같아야 합니다.
2. 루트 디렉터리를 물리 엔트리 순서로 열거하고 `retained_files`가 아닌 파일과 디렉터리를 제거합니다. 디렉터리는 같은 규칙으로 깊이 우선 제거합니다. 제거되는 SFN과 연결된 LFN 엔트리는 첫 바이트만 `0xE5`로 바꾸고 나머지 31바이트는 유지합니다. 제거되는 모든 클러스터 체인은 각 FAT 미러에서 12비트 값만 `0x000`으로 만들며, 같은 3바이트 쌍에 든 이웃 엔트리의 4비트는 보존합니다. 데이터 클러스터는 지우지 않습니다.
3. 유지 파일의 디렉터리 엔트리·FAT 체인·논리 내용·EOF 뒤 클러스터 바이트는 변경하지 않고, 선언된 길이와 SHA-256을 다시 확인합니다.
4. `placed_files` 배열 순서대로 결과 파일을 씁니다. 각 파일은 루트 엔트리를 0번부터 다시 훑어 첫 바이트가 `0xE5` 또는 `0x00`인 첫 32바이트 슬롯 하나를 사용합니다. 새 LFN은 만들지 않습니다.
5. 새 SFN 엔트리의 이름은 문자열 이름이면 stem과 확장자를 각각 8바이트와 3바이트로 공백 패딩하고, `raw_sfn_hex`이면 선언한 11바이트를 그대로 기록합니다. 속성·예약 필드·생성/접근/수정 시각·상위 클러스터는 `0`이고, 시작 클러스터·파일 길이는 리틀 엔디언입니다. 길이 0인 파일은 시작 클러스터가 `0`이고 클러스터를 할당하지 않습니다.
6. 첫 클러스터 검색 힌트는 `2`입니다. 힌트부터 마지막 데이터 클러스터까지 FAT 값이 `0x000`인 첫 클러스터를 고르고, 없으면 `2`부터 힌트 직전까지 다시 찾습니다. 할당할 때 이전 클러스터는 새 클러스터를 가리키고 새 마지막 클러스터는 `0xFFF`가 되며 모든 FAT 미러에 같은 12비트 값을 씁니다. 다음 검색 힌트는 방금 고른 클러스터에 `1`을 더한 값이고 다음 파일에도 이어집니다.
7. 할당된 클러스터에는 논리 파일 길이만큼만 결과 바이트를 순서대로 씁니다. 마지막 클러스터의 EOF 뒤 바이트는 0으로 채우지 않고 그 시점 작업 이미지의 바이트를 유지합니다.
8. 이미지 크기·원본 BPB·동일한 FAT 미러·정확한 루트 파일 집합·각 파일 바이트를 다시 확인하고, 전체 이미지가 `target.sha256`과 일치할 때만 결과를 제공합니다.

따라서 결과에서 달라질 수 있는 곳은 제거 엔트리의 삭제 표식, 해제·재할당된 FAT 엔트리, 새 SFN 엔트리와 배치 파일의 논리 내용뿐입니다. EOF 뒤 여유 바이트와 미할당 영역은 사용자의 원본 작업 이미지에서 유래하며, 제작자의 content HDM에 있던 여유 공간이나 미할당 데이터는 읽지도 복사하지도 않습니다.

## 제작 계획

작성 도구의 `plan.json`은 배포 파일이 아니라 제작 입력입니다. 배포 레시피와 공통인 `id`, `title`, `output_filename`, `source`를 가지며 `assembly.placed_files[].transform`은 다음 둘 중 하나만 선언합니다.

새 계획은 `format`에 `retrogame-patcher-pc98-fat12-raw-sfn-file-bps`를 명시하고 각 배치 파일에 `patch_key`를 둡니다. `format`을 생략한 기존 계획은 ASCII 호환 형식으로 해석하여 이미 공개한 패키지 바이트를 재현합니다.

```json
{ "kind": "copy" }
```

```json
{ "kind": "bps" }
```

제작 도구는 다음 값들을 직접 계산해 ZIP 내부 `recipe.json`을 완성합니다.

- 각 BPS 목표 파일의 길이와 SHA-256
- 결정론적으로 재조립한 전체 결과 HDM의 길이와 SHA-256
- 파일별 BPS와 결합 메타데이터

`copy`로 선언한 파일이 content HDM에서 달라졌으면 제작을 거부합니다. content HDM의 선언되지 않은 파일, FAT 배치, 클러스터 여유 공간과 미할당 바이트는 제작 결과에 영향을 주지 않아야 합니다.

## 입력 제한

현재 참조 구현의 상한은 다음과 같습니다.

| 대상 | 최대값 |
| --- | ---: |
| 원본·content·결과 HDM | 32 MiB |
| `recipe.json` 또는 `plan.json` | 1 MiB |
| 파일별 BPS | 65 MiB 전역 상한 안 |
| 해제한 모든 BPS 합 | 65 MiB |
| 패치 ZIP 전체 | 67 MiB |
| 패치 세트 ZIP 전체와 내포 패키지 해제 합 | 256 MiB |
| `patch-set.json` | 1 MiB |
| 패치 세트 구성원 | 32개 |
| BPS 메타데이터 | 64 KiB |
| ZIP 항목 수 | 4,096 |
| BPS 동작 수 | 파일당 1,000,000 |
| LHA 항목 수 | 4,096 |
| 제거할 FAT 디렉터리 깊이 | 64단계 |

의미 있는 ZIP 항목은 선언 해제 길이와 실제 읽은 길이가 같아야 합니다. 크기 합, 범위, 상대 오프셋과 동작 수 계산의 넘침도 오류입니다. 무관한 ZIP 부가 파일은 해제하지 않습니다.

## 적합성 확인

참조 작성 도구는 `recipe.json` 뒤에 출력 이름순 BPS를 쓰고, 고정 시각·권한과 Deflate 레벨 6을 사용해 같은 논리 입력에서 같은 ZIP 바이트를 만듭니다. 소비자는 ZIP 시각, 항목 순서나 외부 파일명에 의존하면 안 됩니다.

배포 후보는 최소한 다음을 확인해야 합니다.

- ZIP을 다시 열어 레시피·항목 집합·각 BPS 결합을 검사하는가
- 지원 원본에 자체 적용한 결과가 생성 시 조립한 결과와 바이트 단위로 같은가
- 다른 원본, 누락·추가·중복 BPS, 다른 파일·레시피의 BPS와 CRC·범위 오류를 거부하는가
- 같은 논리 파일을 가진 두 content HDM의 비파일 영역이 달라도 같은 ZIP을 만드는가
- 원본 입력 바이트를 변경하지 않는가
- ZIP에 원본·content·결과 미디어가 들어 있지 않은가
- 공개 적합성 벡터의 패키지 바이트와 네이티브·WASM 결과 바이트가 모두 일치하는가

패키지 검사와 정적 빌드는 작품의 에뮬레이터 실행, 플레이 테스트, 사람 검수나 릴리스 승인을 대신하지 않습니다.

## 공개 적합성 벡터

저작권 게임 데이터를 포함하지 않는 합성 FAT12 입력·제작 계획·패치 ZIP·기대 결과와 각 SHA-256을 두 공개 벡터에 고정합니다.

- [ASCII 호환 벡터](../conformance/manifest.json)는 기존 루트 파일 BPS, `empty` 입력 신규 파일 BPS, `placed_files` 순서, SFN 엔트리, FAT12 체인과 EOF 뒤 클러스터 바이트 보존을 검증합니다.
- [원시 SFN 벡터](../conformance/raw-sfn/manifest.json)는 MZ 뒤 LHA에서 CP932 원시 이름 멤버 선택, 안전한 `patch_key`, 정확한 11바이트 SFN 기록과 새 형식 BPS 결합을 검증합니다.
- [패치 세트 벡터](../conformance/package-set/manifest.json)는 앞의 두 단일 패키지를 바이트 그대로 내포하고, 뒤섞인 원본·이미 적용된 결과를 이름 없이 SHA-256으로 분류해 두 목표를 모두 재현하는지를 검증합니다.

네이티브 적합성 테스트는 저장소에 고정한 각 계획·입력·목표로 패치 ZIP을 다시 만들어 ZIP 바이트까지 비교한 뒤, 그 ZIP을 입력에 적용해 목표 HDM과 바이트 단위로 비교합니다. 패치 세트도 두 기존 내부 ZIP 바이트를 바꾸지 않고 고정된 상위 ZIP을 다시 만들어야 합니다. WASM 적합성 테스트는 세 벡터의 입력·ZIP·목표를 사용합니다. 다른 플랫폼이나 미래 구현도 지원하는 각 형식 벡터의 패키지와 목표 바이트를 재현해야 합니다.

같은 `format`을 구현하면서 공개 벡터와 다른 패키지 또는 결과 바이트를 내는 구현은 비호환입니다. 앞으로 내부 라이브러리·컴파일러·운영체제가 바뀌어도 이 검사를 통과한 결과만 같은 동작으로 인정합니다. 기존 결과를 의도적으로 바꿔야 하는 실제 호환성 경계가 생기면 기존 `format`의 의미를 조용히 바꾸지 않고 새 형식 식별자를 정의합니다.

## 현재 범위 밖

FDI·HDI 같은 컨테이너, 크기가 다른 목표 이미지, 결과 하위 디렉터리, MZ 뒤 LHA 이외 설치 압축, raw-sector 로더·보호 데이터와 파일 바깥 영역을 의도적으로 바꾸는 패치는 현재 프로토콜에 포함하지 않습니다. 그런 용례는 파일 BPS에 억지로 넣지 말고 별도 명시적 영역 계약이 필요합니다.

웹 사이트는 사용자가 고른 패치 ZIP과 원본 HDM만 로컬 입력으로 사용하며 작품별 ZIP을 서버에서 자동 선택하는 호스팅 모드를 제공하지 않습니다.
