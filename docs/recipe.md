# 레시피 계약

레시피는 어느 원본에서 어떤 파일을 가져와 어떤 순서로 기준 HDM을 만들고, 어느 BPS 결과를 허용할지를 고정합니다. 작성 도구는 이 파일을 BPS와 함께 표준 ZIP에 넣습니다. 알 수 없는 JSON 필드는 오류입니다.

## 배포 ZIP

작품별 배포물은 일반 ZIP 파일 하나입니다. 패처가 소비하는 두 파일은 ZIP 루트에 둡니다.

```text
<작품명>-kr-patch.zip
├── recipe.json
└── patch.bps
```

내부 이름은 대소문자까지 정확히 고정합니다. 필수 항목의 누락·중복·하위 디렉터리 배치는 오류입니다. `README.txt` 같은 다른 항목은 패처가 읽거나 압축 해제하지 않습니다. 작성 도구는 필수 두 항목만 넣으므로 원본이나 완성 HDM을 배포 ZIP에 포함하지 않습니다. 외부 ZIP 파일명은 사람이 알아보기 위한 이름이며, 패처는 그 이름으로 작품이나 판본을 판정하지 않습니다.

ZIP 전체 크기와 항목 수, `recipe.json`과 `patch.bps`의 압축 해제 크기에는 브라우저 적용용 자원 한도가 있습니다. 필수 항목은 암호화 ZIP과 지원하지 않는 압축 방식을 허용하지 않으며, 선언한 압축 해제 크기와 실제로 읽은 크기가 달라도 중단합니다. 이 한도는 무관한 부가 파일의 존재를 금지하려는 것이 아니라 ZIP·JSON·BPS 파싱이 메모리와 실행 시간을 무제한 소비하지 못하게 하는 경계입니다.

## 최상위 필드

| 필드 | 의미 |
|---|---|
| `id` | BPS 메타데이터에도 기록되는 패치 식별자 |
| `title` | 웹 화면에 표시할 작품명 |
| `output_filename` | 다운로드 파일명. 경로는 허용하지 않음 |
| `source` | 지원 원본 이미지의 정확한 정체와 FAT12 형상 |
| `assembly` | 기준 HDM의 파일 구성과 해시 |
| `target` | 최종 결과 이미지의 크기와 SHA-256 |

SHA-256은 소문자 64자리 16진수만 받습니다. DOS 파일명은 대문자 8.3 형식으로 제한합니다.

## 원본과 FAT12 형상

`source.size`와 `source.sha256`이 먼저 일치해야 합니다. `geometry`에는 BPB에서 읽은 다음 값을 모두 기록합니다.

- `bytes_per_sector`
- `sectors_per_cluster`
- `reserved_sectors`
- `fat_count`
- `root_entries`
- `total_sectors`
- `media_descriptor`
- `sectors_per_fat`
- `sectors_per_track`
- `heads`

`mount_policy`는 일반 FAT12의 `standard` 또는 후기 BPB 필드를 부트 코드로 쓰는 PC-98 DOS 3.x용 `pc98_dos3`입니다. 후자는 마운트용 복사본만 보정하며, 결과의 예약 영역은 원본 바이트로 되돌립니다.

## 파일 조립

`assembly.retained_files`는 원본 루트에서 위치와 속성까지 그대로 남길 파일입니다. 각 항목은 `name`, `size`, `sha256`을 가집니다.

`assembly.placed_files`의 배열 순서는 실제 작성 순서입니다. 이 순서를 고정해야 FAT 클러스터 배치도 결정론적으로 재현됩니다. 각 항목은 출력 `name`, 결과 `size`와 `sha256`, 그리고 다음 중 하나인 `source`를 가집니다.

```json
{ "kind": "root_file", "name": "GAME.COM" }
```

```json
{
  "kind": "mz_lha_member",
  "container": "INSTALL.EXE",
  "member": "GAME.COM"
}
```

각 파일의 선언 크기와 최종 루트 파일 전체 크기는 원본 HDM보다 클 수 없고, 최종 루트 파일 수는 BPB의 루트 엔트리 수를 넘을 수 없습니다. MZ 뒤의 LHA에서는 레시피가 실제로 요청한 멤버만 압축 해제하며, LHA 헤더의 원본 크기와 레시피의 파일 크기가 먼저 일치해야 합니다. 같은 컨테이너·멤버를 서로 다른 크기로 선언하면 적용 전에 중단합니다.

조립 시 유지 대상으로 선언되지 않은 루트 파일과 디렉터리는 작업 복사본에서 제거됩니다. 원본 배열은 변경하지 않습니다. 완료 뒤에는 다음을 다시 확인합니다.

- 이미지 크기와 BPB 형상
- 모든 FAT 미러의 동일성
- 루트 파일 집합
- 유지 파일의 크기와 해시
- 배치 파일의 전체 바이트
- `assembly.baseline_sha256`

## BPS 결합

BPS 메타데이터에는 레시피 전체가 아니라 레시피 ID, 원본 SHA-256, 기준 HDM SHA-256, 목표 SHA-256만 들어갑니다. BPS의 소스는 `assembly.baseline_sha256`으로 식별되는 정규 기준 HDM이고, 목표는 `target.sha256`으로 식별되는 결과 HDM입니다. 적용 시 BPS 헤더 크기, 메타데이터 크기, 정규 가변 길이 정수, 동작 수와 각 읽기·쓰기 범위, 남는 동작 바이트의 부재, 소스·목표·패치 CRC32와 목표 SHA-256을 모두 확인합니다. 목표 HDM도 FAT12 형상과 FAT 미러가 정상이어야 레시피에 채택할 수 있습니다.

ZIP은 레시피와 BPS를 한 파일로 전달할 뿐 BPS의 의미를 바꾸지 않습니다. 일반 BPS 도구로 `patch.bps`를 검사할 수 있지만, 사용자 원본을 먼저 정규 기준 HDM으로 재조립해야 하므로 원본 HDM에는 이 패처를 통해 적용합니다.

현재는 원본과 목표의 이미지 크기가 같아야 합니다. FDI·HDI 컨테이너 파싱, 하위 디렉터리에 새 파일 배치, 임의 압축 형식은 아직 계약에 포함하지 않습니다.
